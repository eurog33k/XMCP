# Changelog

All notable changes to XMCP will be documented here.

## [Unreleased]

### Fixed
- **Enum values with no explicit number were dropped.** The text reader only recorded a value when the line contained `" = "`, so `fatal` / `error` / `warning` produced nothing while `InternalError = -32603` worked — and the implicit form is the common one, since Xojo only writes the number when someone pinned it. An enum came back with a name and an empty body. Implicit values now take their ordinal the way Xojo assigns it: from zero, or on from the last value that was written down. Measured against a real project whose fourteen enums all returned empty
- **A control was listed by name and not findable by it**, while the handler beneath it resolved — so the child was reachable and its parent was not. Decided rather than excluded: naming a control now returns the control and every handler under it, which is what asking about a control means. The invariant in `FindMembers` records the decision, so the next person applying it does not have to guess whether a control was meant to be carved out
- **The multi-match header claimed an overload for matches that were not one.** A control returned with its handlers is several matches of different kinds, and describing it as "2 declarations, get_code returns the first" described something that was not happening. The header now checks whether the matches really are all methods before saying so
- **Three more kinds of member were listed but not findable.** `describe_item` on a window property answered "has no member called X" about a property the same window's listing prints, and the same was true of enums and notes in a class or module — nobody had reported those two. `FindMembers` keeps one invariant: anything the listing shows *by name* must be findable by that name. Three separate builds have each added one collection to it after someone hit the gap, so the search loops now sit in the same order as the display code and say so, because adding to one list without the other is the actual bug
- **An array property was reported as a scalar.** The `()` marker sits in both `<ItemName>` and the declaration and reached neither the parsed name nor the output, so `profileStack() As TUProfileData` read as `profileStack As TUProfileData` — a caller was told the property holds one item rather than a list. Method return arrays were unaffected; this was specific to properties
- **A shared property lost its `Shared` keyword, or kept it as part of its name.** `XKProperty` had no `IsShared` field at all, so neither reader could represent one: the XML reader dropped it, and the text reader appeared correct only because the keyword was glued to the name it parsed — leaving the property unreachable by path, the same fault the scope keyword had. Both readers record it now and it renders explicitly
- **Properties now render through one function** used by container listings and by member-path lookups alike, so the three sites cannot drift. The one deliberate difference is that a default value appears only when the property is asked for by name: a listing is a summary, defaults can be long, and values that look like credentials do not belong in output nobody asked for them in
- **Properties and constants could not be reached by member path.** `describe_item` on `Owner.SomeProperty` answered "has no member called SomeProperty" about a member its own container listing showed on the next line — `FindMembers` searched methods and events only. Properties, computed properties and constants are searched now, and a member with no body no longer reports "(empty body)", which described an absence where there was nothing to be absent
- **Member scope was reported only when the file format happened to spell it out.** The text format writes the keyword into the declaration line (`Protected mConnected As Boolean`) while the XML format keeps it in `ItemFlags` — so the same module read one way showed `Private m_strAppName` and the other way `m_strAppName`, with nothing signalling that scope was unavailable rather than public. Both carry the flags; scope is now read from them. It also means the text reader is no longer storing `Protected mConnected` as a property's *name*
- **Constants in XML items lost their values.** The value lives in `<ItemDef>`, which was never read — only a declaration-based fallback that XML constants do not have. Verified against real files: a constant declared `-1` in the XML now reads `None = -1`, and an eleven-property class comes back with its `Protected` and `Private` scopes intact
- **External items in an XML project were reported as not found.** Xojo writes them as a top-level `<block type="ExternalCode">` holding only a name and two paths, and that block type was not in the XML parser's dispatch — so it fell to the unknown-block branch and was dropped, while `list_project_items`, which asks the IDE, listed the item perfectly well. Resolution prefers `<PartialPath>` over `<FullPath>`: the relative form travels with a checkout, while the absolute one belongs to whichever machine last saved and appears variously as a POSIX path or an old HFS `Macintosh HD:…` path. `PartialPath` uses backslash separators and `..` traversal on every platform, both of which are handled. Verified against real XML projects with externals reached through `..\..\` into a separate directory tree
- **An unreadable item was described as an empty one.** "This item contains no code members" was printed whether the item had none or whether the file behind it could not be read — which for a binary external is the ordinary case. `describe_item` now checks the file first and says which: binary format with the way to change it, or a missing file with why an external item can go absent on a machine that does not have it
- **`describe_item` reported an item's wrapper type rather than its own.** Every code container is written as `<block type="Module">` with `IsClass` and `IsInterface` inside it deciding what the item really is, so a console `App` with `IsClass=1` and `Superclass=ConsoleApplication` was labelled `(Module)`. It now reports Class, Module or Interface as parsed, and an unresolvable external reads `(External item)` rather than Xojo's internal `ExternalCode`
- **`describe_item`'s not-found message asserted two things that were usually false.** It said the item did not exist, when `list_project_items` would list it perfectly well, and advised saving the project as Text or XML on projects that already were. On Windows that advice cost two rounds of investigation before a test matrix made the real cause obvious. It now says the item was not found *in the files*, notes that the IDE and the files can disagree, and names the likely causes in order — starting with an external item inside an XML project, which is a known gap rather than a missing item
- **Items stored as XML were reported as empty.** An external item written in Xojo's XML form (`.xojo_xml_code`, `.xojo_xml_window`) was handed to the `#tag` text reader, which finds nothing in XML — so `describe_item` answered "This item contains no code members" for a 41 KB class with 36 declarations, and `get_code` and `list_project_items` had nothing to fall back on either. The project format is not the deciding factor: a **text** project routinely holds XML external items, which is the usual shape for code shared between projects under version control. External items are now detected by content and parsed with the XML reader, which gains a public entry point for a single item file. Found on Windows against real `MyJSONItem.xojo_xml_code` and `clsHTTPRequest.xojo_xml_code`; reproduced and fixed on macOS against a hand-built equivalent
- **`stop_project` could not see a running debug build on Windows**, so it reported "nothing was running" for a process confirmed by PID, and its terminate-directly backstop could never engage. Two independent faults in one filter, either of which was enough: the debug build's name differs by platform - macOS and Linux produce `AppName.debug`, Windows produces `Debug<AppName>.exe`, which contains no `.debug` at all - and the path comparison was case-sensitive against a path that arrives in 8.3 short form from `ProjectShellPath` while `Win32_Process` reports the long form. The naming test is now platform-aware and checks the executable's own name; the path test is case-insensitive with the project folder's real name as a fallback. Measured on Windows 11 with Xojo 2026r1.1 against a live `C:\tmptest\browntest6\Debuguseit\Debuguseit.exe`; the macOS path, which always worked, was re-verified after the change. Pre-existing, and invisible until the message stopped describing both outcomes identically
- **Top-level items inside a folder could not be deleted.** The Navigator guard compared the IDE's `ProjectItem` - which answers with the folder-qualified `Tools.EstimateRequestCost` - against the unqualified path XMCP uses, as equals. In a real project that refuses most items. Only the leaf is compared now, which still catches the case the guard exists for
- **A partial IDE delete escalated into file surgery and destroyed both declarations.** Measured on macOS with Xojo 2025r3.1: one declaration on disk, a second held unsaved in the IDE. `DeleteSelection` removed one in memory, the name stayed reachable through the other, so the tool read that as failure and fell through to the file route - whose save committed the partial delete and whose scan then cut the survivor. Disk went from one declaration to none under a `Deleted:` message. macOS now stops at that point and says what is known, since refusing cannot destroy anything
- **`describe_item` could not see windows that predate API 2.** Three places were keyed to the API 2 spellings only - the manifest item-type gate, the type dispatch, and the `.xojo_window` reader, which skips forward to `Begin DesktopWindow` and so ran off the end of a classic file, parsing nothing from it. Any desktop project written before API 2 had windows XMCP reported as absent rather than unreadable. Fixed for windows, containers and toolbars in both the text and XML parsers; the XML half is unverified for want of an XML-format project
- **The macOS install produced a binary macOS refuses to run.** Xojo signs the build folder ad hoc, so copying `usage-guide.md` in next to the binary - which is the documented step - invalidates the signature, and the process is then killed on launch with `Killed: 9` and no output. The install now re-signs and verifies, and both places that describe it say so
- **The usage guide contradicted itself on overloads**, telling the reader in adjacent paragraphs that `describe_item` shows every declaration and that they should hand-parse the `.xojo_code` file, and described `stop_project`'s verification and backstop with no hint that neither reached Windows
- **A refused member delete could damage the source file, and reported that it had not.** `DoCommand("DeleteSelection")` is documented as not implemented off macOS, which was read as *does nothing*; on Windows it edits the **text at the caret**. The member path focused the editor, sent it, saw the member still present, and fell through to the file route — whose save then committed the caret damage to disk before the ambiguity check declined to touch anything. Measured on Windows 11 with Xojo 2026r1.1: a character vanished from the body of the focused method, only `build_project` noticed (nothing else reads method bodies), and the message said `Nothing was deleted`. `DeleteSelection` is now sent on macOS and nowhere else. The same silent guess was reachable on macOS by a different route — there it removes whichever overload the editor resolved to, the name stays reachable through the other declaration, so the tool concludes failure and falls through to the file route, whose save commits that removal and whose scan then finds one declaration left and cuts it too. Both routes now establish the declaration count before anything is touched, and the scan never writes, so a refusal leaves the file byte for byte as it was
- **Reading the project files no longer saves them.** Every file-reading tool saved first, which made `revert_project restores it` a promise no such tool could keep: a member deleted through the IDE stays undoable until something saves, and inspecting the result was the something. `describe_item`, `list_project_items` and `get_code`'s fallback now report what is on disk and say so. The trade is stated where it matters — an unsaved delete still appears until you save
- **The file route's refusal wrote before it declined.** `delete_project_item`'s fall-through saved, then scanned, then refused. Measured on Windows: a call reporting `Nothing was deleted` took the file from one declaration to two, committing pending IDE state the caller could still have discarded. Every reason to decline is now established against the files as they are; the save happens only once writing is the intent. It cannot be removed entirely — the route cuts a block out of a file and reloads, so the file must match the IDE first — so when that save is what changes the answer, the refusal says so
- **`stop_project` described both outcomes in the same words.** It now counts what was running before the Kill, so "stopped a debug session" and "there was nothing to stop" are distinguishable
- **`save_project` implied a write that may not have happened.** The IDE has no command reporting whether it had unsaved changes, so the message now claims only what is known: the files on disk match the IDE
- **`select_project_item` gave a folder the method-level explanation** — and a workaround (`get_code`) that cannot apply to one. It now works out which condition it hit
- **Event handlers printed as bare names** in all three places that list them, dropping their parameters without saying so; `UserInterfaceUpdate(data() As Dictionary)` appeared as `UserInterfaceUpdate`
- **`create_project_item` rejects `AddEventImplementation`** instead of stalling. Xojo documents it; it never answers and blocks the connection for the full timeout, after which nothing has been created. The refusal names the file-editing route to an event handler instead

### Changed
- **The version identifies the build.** `NonRelease` is stamped from the commit count and the MCP handshake reports four components (`1.3.0.34`), so two binaries can be told apart without comparing file sizes

## [1.3.0] - 2026-08-24

### Added
- **`describe_item` tool, and file-parsing fallbacks for `get_code` and `list_project_items`.** Four things IDE scripting cannot answer are now answered by parsing the project files: a class's members, a method's signature, whether a name is overloaded, and anything inside a `.xojo_window` — including control event handlers and the control tree. `describe_item` always reads the files; `get_code` and `list_project_items` fall back to them when the IDE returns nothing. Built on XojoKit by Garry Pettet, vendored in `src/XojoKit` — the same parser behind his `xojotool`
- Tools that read the files **save the project first**, because the IDE cannot be asked whether it has unsaved changes. Each says so in its output. Two consequences come with it: a pending on-disk edit is overwritten by the IDE's copy unless `revert_project` is called first (documented and deliberate), and a project whose `RBProjectVersion` is newer than the running IDE is never saved — that would rewrite it in the older format, so the save is skipped and the staleness reported instead. Text and XML projects are readable; binary is not
- `set_declaration` tool wrapping `ChangeDeclaration` — sets a method or property's name, parameters, return type, scope and `implements`. `create_project_item` creates an unnamed `Untitled` item and `set_code` writes bodies only, so until now a method created through XMCP could not be given a signature at all. The three together (create, declare, set body) produce a compiling method, verified end to end
- `delete_project_item` deletes top-level items on both platforms. It selects the item in the Navigator and issues the undocumented `DoCommand("Delete")` — the manual lists only `DeleteSelection: Not implemented`, which is accurate for Windows. Members (a method or property inside a class or module) still need `DeleteSelection` and so remain macOS-only; on Windows the tool refuses and names the disk route. Crucially it never fires `Delete` for a member path: `SelectProjectItem` returns False there and leaves the Navigator on the *parent*, so doing so would delete the containing class or module. `ProjectItem` is compared with the intended item before anything is deleted
- `delete_project_item` tool — `create_project_item` was one-way, so a mistakenly created item could only be removed by hand in the IDE. `DoCommand "DeleteSelection"` returns nothing, so the deletion is verified by checking the item can no longer be reached. **macOS only**: Xojo documents that command as "Not implemented", which is exactly what it is on Windows, where the tool reports failure and changes nothing. On macOS it deletes precisely the named item — verified against a module holding two methods plus a sibling class, where only the named method disappeared
- `docs/USING-XMCP.md` — a practical guide to working on a Xojo project through XMCP: the two-copies mental model, a first session, the two edit routes and how not to lose work, debugging built apps, platform differences, and troubleshooting
- `select_project_item`, `get_code` and `set_code` now reach methods, properties and event implementations. They navigate by assigning the IDE's `Location`, which reaches members, instead of relying on `SelectProjectItem`, which only reaches top-level items and silently failed on anything deeper. A path that does not exist is reported rather than silently reading the previously selected item
- `revert_project` now works on Windows. Reloading needs the project closed and reopened, and closing the last project window quits the Xojo IDE there - so the close is performed while a generated throwaway project (`%TEMP%\XMCP Host`, stamped with the IDE's own version so it opens without warnings) holds the IDE open, then closed again. `OpenFile` on an already-open project focuses it without reloading, which is what makes the ordering controllable, and every step is verified against `ProjectShellPath`
- `save_project` tool — saves the IDE's in-memory project to disk via `DoCommand "SaveFile"`. Together with `set_code` this gives a complete round trip that needs no project reload, which matters on Windows where `revert_project` is unavailable
- **Windows support.** All platform-dependent paths now live in a new `Platform` module: IPC socket discovery, the debug log location, and the documentation root. Verified on Windows 11 with Xojo 2026r1.1 — MCP handshake, tool listing, IDE connection, documentation lookup, and `revert_project` (against a binary project) all work
- IPC socket discovery now mirrors `FindIPCPath` from Xojo's shipped IDECommunicator v2 example, probing candidate *folders* for writability instead of testing the socket path itself. On Windows the socket resolves to `%LOCALAPPDATA%\Temp\XojoIDE`
- `XOJO_IPCPATH` is now honoured, so XMCP can talk to a specific IDE when several are running side by side
- Connection failures now list every path that was tried and ask whether the IDE is running

### Fixed
- **`delete_project_item` reported deleting members it had not deleted, then stopped being able to delete them at all.** Its existence check returned False both when an item was gone and when the IDE simply did not answer — and a delete suppresses the output of the script that follows it, so the check after `DeleteSelection` went unanswered and was read as success. On Windows, where `DeleteSelection` does nothing, that produced a confident false "Deleted". A later change added a round trip that let the IDE answer truthfully, turning the false success into an honest refusal — which looked like a regression. The check now distinguishes "no answer" from "gone" and is retried until the IDE answers, and members are removed by cutting their `#tag` block out of the `.xojo_code` file where the IDE cannot do it — refusing rather than guessing when the name is overloaded, and stating that this deletion is already on disk
- **`stop_project` never stopped anything, and always said it had.** Its script was `DoCommand "Kill"` followed by `Print "Debug session stopped."` — a fixed string, printed whether or not the app exited. Measured: `Kill` stops a desktop app but leaves a **console** debug build running, so `run_project` on XMCP itself left an `XMCP.debug` process alive after every reported stop. It now verifies by looking for a live executable under the project folder whose path contains `.debug`, terminates it directly when the IDE's Kill did not, and says which happened. It skips XMCP's own executable, so it cannot stop the server answering the request
- **Every boolean tool parameter was rejected.** `MCPKit.TypeFromValue` tested for array, string and numeric and then fell through to "assume it's an object", so JSON `true` and `false` both arrived as `Object_` and any boolean argument failed with *"Expected boolean but received object"*. That made `build_project`'s `reveal` and `get_debug_log`'s `clear` unusable since the day they were written. Fixed in the vendored MCPKit; worth reporting upstream
- **`get_item_description` failed outright whenever a `location` was passed.** Its navigation guard ended with a bare `End`, which is not a statement in XojoScript, so every such call returned a syntax error; and the guard used `SelectProjectItem`, which cannot reach a member, so a method path could not have worked even once the syntax was valid. It now navigates by assigning `Location` with a `SelectProjectItem` fallback, and an item with no description reports that rather than `{}`
- **`search_docs` labelled matches with unrelated headings.** It tracked any line beginning with `#` as a heading, but Xojo ships these docs as reStructuredText: `llms-full.txt` holds 5 Markdown headings, roughly 11,000 RST headings underlined with punctuation, and 700 `#.` enumerated-list markers that were being mistaken for headings. Both styles are now detected, so a `TextInputStream` match is labelled "How do I load and save data to a file?" instead of a list item from 1,500 lines earlier
- `delete_project_item` claimed an existing folder did not exist. IDE scripting cannot select a folder at all — `SelectProjectItem` returns False for one — which is indistinguishable from a bad path unless the parent's `SubLocations` is checked too. It now checks, and reports the real reason
- `get_current_location` answered a bare `()` when nothing was selected, which happens immediately after a delete. It now says so
- `constant_value`'s description promised that a bare name works. It does not: an unqualified name resolves only against the current Navigator selection. Corrected rather than worked around
- `revert_project` on Windows now holds the IDE up with `NewConsoleProject` instead of a hand-written project file. The previous mechanism generated a minimal `.xojo_project` under `%TEMP%\XMCP Host`, stamped with the IDE's version so it would load without warnings; one documented command replaces all of it, writes nothing to disk, and cannot fail to load. `WindowCount` now decides whether a second window is needed at all, so nothing extra is created when the user already has another project open. `Platform.HostProjectFile` and its file-writing helper are gone
- `run_ide_script` no longer presents an empty result as if it were output, and explains the usual cause: **the IDE returns only the first `Print` in a script** and discards the rest. Xojo's protocol documentation says the last value; measured behaviour on 2025r3.1 is the first. A script that prints a status line, runs a command, then prints the result gets the status line back, which reads as though the command produced nothing or aborted the script
- `revert_project` misreported success and failure when a second project was open in the IDE. It checked whether *any* project was open after the close instead of whether the *target* was still open, so with two projects open it closed the project, concluded the close had failed, reported "Nothing was changed", and left the project shut. Both the close and the reopen checks now compare against the target
- **`set_code` and `set_selected_text` were completely broken on Windows**, and `search_docs` and `list_doc_topics` badly degraded there. All four split text with `Split(EndOfLine)`, which is CRLF on Windows, while the text they split is LF-terminated whatever the platform - JSON-RPC payloads use `\n` and Xojo ships its documentation LF-only. The split found no delimiter and returned the whole input as one line: `set_code` emitted a single string literal containing raw line feeds (Xojo compiler error 68, "End quote missing") and the documentation tools collapsed a 1500-line index into one line. A new `Tool.SplitLines` normalises line endings first. `HasTrailingEndOfLine` carried the same assumption and now tests for any line ending
- **`build_project` never actually built anything while always reporting success.** Its build-type table was wrong (`14` is iOS Device, not Windows 64-bit; `9` is macOS Universal, not Windows 32-bit) and `0` was not a valid target at all. It also used `DoCommand "BuildApp"`, which answers `{}` both on success and when the IDE ignores the command. Now uses the `BuildApp(type, reveal)` function, which returns the built path, so success is verifiable; an empty result is reported as a failure
- **`revert_project` reported IDE script errors as success** and assumed the reload happened. It now verifies the project state through `ProjectShellPath` rather than trusting the reply, and reports the resolved project path
- JSON-RPC responses are now terminated with an explicit LF. `Print` is `StandardOutputStream.WriteLine`, which emits the platform `EndOfLine` — CRLF on Windows — while the stdio transport is LF delimited. Incoming lines are trimmed so a CRLF-terminated request does not leave a stray CR on the JSON
- Never probe the IPC socket path with `FolderItem.Exists`: on Windows the endpoint has no filesystem entry, so `Exists` is always `False` even while the IDE is listening. The check survives as a fast path on macOS and Linux only, and a bounded connect timeout rules out wrong candidates elsewhere
- `get_project_info` returns long paths on Windows instead of the 8.3 short paths that `ProjectShellPath` hands back

### Known limitations
- `get_system_log` is macOS only and is no longer registered elsewhere (Windows exposes 21 tools instead of 22). `System.DebugLog` goes to `OutputDebugString` on Windows, which only an attached debugger sees — use a file-based `App.UnhandledException` handler with `get_debug_log`
- `revert_project` does not work on Windows. Every reload route was tested: `CloseProject` + `OpenFile` reloads but quits the IDE when it closes the last project window; `DoCommand "Revert"` is undocumented, needs a pending change, and always raises a modal confirmation that blocks the IDE's script engine; re-opening the same project with `OpenFile` is a silent no-op. The tool fails explicitly without touching the IDE
- Do not set `XOJO_AUTOMATION=TRUE` on Windows — the IDE exits immediately after loading a project

## [1.2.0] - 2026-02-24

### Added
- MCP `resources` protocol support: `resources/list` and `resources/read` — clients can now fetch `usage-guide.md` as an MCP resource at session start
- `get_project_info` now returns a `Project Directory:` line with the full path to the project folder, enabling direct file editing workflows
- `usage-guide.md` is now distributed next to the binary and exposed as an MCP resource — AI clients receive it automatically; users can edit it without rebuilding

### Fixed
- Shell injection prevention in `get_system_log`: `process_name` parameter is now validated against a whitelist regex before interpolation into the shell command
- JSON-RPC `id` type preservation: integer ids are now correctly echoed back as integers (not coerced to strings), fixing protocol compliance
- `ToolParameter.ToJSONItem` now emits correct JSON types for Boolean and Integer defaults (not always String)
- `MCPKit.Error()` now emits JSON `null` for missing ids instead of an empty string
- `get_selected_text` and `set_selected_text` now return `Failure` instead of `Success` when the IDE returns an `ERROR:` string
- RequestID lookup fixed: integer ids no longer cause the server to exit with "Missing id" on subsequent requests

### Changed
- `get_system_log` now works for both debug builds (`AppName.debug`) and built apps (`AppName`) — not just debug builds as previously documented
- Actionable error messages in `select_project_item`, `get_code`, and `set_code`: errors now guide the AI to the correct alternative strategy (direct file editing, `revert_project`, etc.)
- `usage-guide.md` expanded with tested guidance: window event handler file format, `list_project_items` event limitation, debug vs. built app logging behavior

## [1.1.0] - 2026-02-23

### Added
- `get_debug_log` tool: reads crash/exception info written by `App.UnhandledException` handlers to `/tmp/xmcp_debug.log`
- `get_system_log` tool: reads `System.DebugLog` output from the macOS unified log for a named debug app process (e.g. `MyApp.debug`)

### Fixed
- `build_project` now correctly passes build type and reveal flag to `DoCommand "BuildApp"` as a single string argument (e.g. `"BuildApp 24 True"`) — comma-separated arguments caused a script compiler error
- XMCP server processes now terminate gracefully when the MCP client closes stdin, preventing zombie processes from accumulating
- `run_project` and `build_project` now correctly capture and report compile errors from the Xojo IDE instead of always returning success
- Error output is formatted as a readable list with error type, message, location, and position

### Changed
- `search_docs` description clarified: it searches guides and tutorials, not the API reference — use `lookup_class` for class/method/property lookups

### Added
- Initial release with 20 tools for controlling the Xojo IDE via MCP
